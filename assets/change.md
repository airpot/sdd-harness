# Change Record

Keep the project's format. Do not include fields that are not applicable.

Writing policy: <accessible-writing-policy-reference>.
Before you keep this record, replace this placeholder with the project's policy reference or an installed skill policy.
Use this record's directory at its destination as the base directory for local links. Make sure that the next reader can read the policy.

Do not change identifiers or raw evidence.
Collaboration fields or setup are not necessary for tasks that you do independently.

For applicable fields, use these instructions:

- Change and task ID: give stable references.
- Goal and scope: write the user requirement, change, and boundaries.
- Accepted basis: give references to specification, interface, and code baseline versions.
- Structure at entry: identify related entry points, components that you can use again, and behavior to keep.
- Specification review: record important conflicts, assumptions, boundaries, non-goals, and applicable constraints.
- Coverage: give the relation from source requirements to acceptance conditions, tasks, implementation, and evidence. Use inline references or a coverage table that helps the task.
- Acceptance conditions: write results that the reader can see and the validation methods.
- Assertion basis: give references to accepted expected results, counterexamples that help the task, and defect reproduction if applicable.
- Risk checks: find necessary system, performance, security, compatibility, and recovery evidence. Do not include checks that are not applicable.
- Dependencies and shared contracts: identify work that occurs at the same time and results necessary before integration.
- Optional delegation: give references to worker goals, basis identities, write scopes, mandatory results, and limits. Give references to the main agent's duty for acceptance.
- Optional cooperation: give the relation from component scope, developer responsibility, and integration duty to the full business outcome and contract.
  Include the accepted contract.
- Integration: give references to the target at integration and the combined candidate, with applicable validation of this candidate.
- Execution: identify the task, checkout, harness, and owner. Record observations of activity at execution.
  This record gives no ownership control.
- Runs with important effects: keep available model/provider, skill, tool, and related configuration metadata with no secrets.
  Before you try again, record the failure classifications of the attempts.
- Results and evidence: give references to commits or snapshots, acceptance conditions, validation-object identities, methods, environments, results, and logs.
- Validation recipe: record executable steps, necessary input versions, setup, and pass criteria.
- Evidence applicability: record the conclusion at review and the reason that evidence from before the change is applicable.
- Acceptance: record scope with acceptance for all conditions, acceptance for some conditions, or `blocked` results.
  Keep each mandatory condition with a `failed`, `blocked`, or `not run` result in the record.
- Specification reconciliation: identify the record with specification authority, maintenance model, accepted updates, and remaining gaps.
- Requirement operations: identify related additions, modifications, removals, renames, and accepted transition conditions.
- Work without verification, `blocked` work, or work for subsequent execution: write effects, reasons, recovery conditions, and follow-up tasks.
- Next action: give the step and necessary inputs.
