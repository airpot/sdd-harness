# Internal Document Writing Policy

## Scope and precedence

Use English for internal development prose that you write or change during work with this skill.
This includes specifications, plans, design decisions, interface descriptions, validation records, handoff records, release records, and recovery instructions.
Use the policy for changed sections.
If documents from before the task have no relation to its changes, do not change their language.

Obey language instructions that the user gives and mandatory project formats.
If a project rule makes a different language mandatory, keep this language. Record the exception in a short statement.
Do not replace an accepted specification only to change its language.
Unless the user tells you to use a different language, keep conversation in the user's language.

Do not change source quotations, identifiers, API fields, commands, paths, logs, or tool results.
Write explanations in the language from this section's precedence rules.
Do not use this policy to change program behavior, evidence, authorization, or acceptance conditions.

When you make these records, keep the policy reference in the development instructions or policy location that the project uses.
For a small change, the task record that the project uses can contain this reference.
Use a project policy reference or a policy reference for an installed skill. Make sure that the reader can read the policy.
For a small change, do not make a new policy document.

If project setup makes a policy location mandatory and there is none, use `.sdd-harness/project.md`.
If an accepted project convention gives a different location, obey this convention.
Do not make policy documents with the same contents. Do not change global agent configuration.

Asset templates contain a policy placeholder because projects can have different destinations.
Before you keep a record, replace its placeholder with a policy reference. Use a project policy reference or a policy reference for an installed skill.
The reader must have access to this policy.

Use the kept record's directory as the base directory for local links. Make sure that the reader for this record has access.
The project's policy is the authority for these records. Templates are optional.

## Use all STE rules and vocabulary

Use all 53 writing rules in ASD-STE100 Issue 9.
Also use its dictionary and eight general recommendations.
The checkpoints in this policy give project implementation guidance. They do not replace the official standard.
Before the review, read the official explanations, exceptions, and dictionary introduction.

Examine the words in each passage. Equal spelling does not give dictionary approval for the meaning in this passage.

For each English word that you write, examine its base, part of speech, meaning, forms, and restrictions.
For each technical term, give its category, domain meaning, and use in the passage.
Use a technical noun only as a noun or as part of a technical noun.
Use a technical verb only for the domain process in its definition.
When an approved construction gives the same meaning, use this construction.
A technical category gives no exception for verbs, adjectives, or adverbs that are not technical terms.

Do not change computer code, commands, paths, identifiers, labels with mandatory text, or mandatory source quotations.
Examine comments, docstrings, CLI help, diagnostics, template prompts, and new instructions in quotations as prose that you write.
For an example of incorrect English, identify its quotation boundary. Record its purpose as an example of incorrect English.
Quotation marks are not sufficient evidence for protection of a new instruction.

These recommendations are different from the 53 rules.
Use the [official standard](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf) for full explanations and vocabulary evidence.
The [official overview](https://www.asd-ste100.org/about_STE.html) gives an introduction to STE.

For a full review, include all of the identified corpus.
Include the frontmatter, prose, labels, templates, script comments, docstrings, help, and diagnostics.
Record decisions about the words in their passages, with source page references. Do not put dictionary columns in the review record.
For each rule, record a pass, failure, inapplicability with its reason, or an `unresolved` result.

Identify the method, scope, and source of each format check, script check, model evaluation, and semantic review. The results can be the same.

A review with gaps stays `unresolved`. A short sentence or dictionary match is not sufficient evidence of conformance.

If you cannot get source evidence, keep the text clear. Give a report of the missing review.
Until a full review gives evidence for conformance of an identified scope, use the label `STE-guided English`.
Record such a claim with the identities of the corpus in the review, source version, and STE issue.

A project review is not official certification. It gives no conformance evidence for text that you subsequently write.
If distribution permission is missing, do not include the official standard or dictionary in project artifacts.

The three technical verbs in this section use category 2(c), computer system operations.
The meaning of `integrate` is code integration into an identified baseline.
Its meaning does not include a general procedure to make items part of a group.

First examine the approved dictionary meaning of `deploy` (storage to operation).
If it is necessary, use the computer-process route.
For this route, the meaning of `deploy` is application of a candidate to its target runtime.
Its meaning does not include a general change of responsibility.

The meaning of `restore` is reconstruction of kept computer results.
Its meaning gives no general recovery guarantee.

Make sure that each technical verb is necessary in its passage. When an approved construction accurately gives the same process, use it.
Do not change CLI names or API identifiers. Their grammar can be different from prose.

## Review meaning and evidence

These checks are also project requirements. Obey them with the STE writing rules:

1. If responsibility can cause ambiguity, identify the actor. Do not add an unknown actor only to make active voice.
2. Give the condition, action, object, and result that an observation can show for important procedures.
3. Identify the status and authority of requirements, proposals, observations, and accepted decisions. Their content can be the same.
4. For evidence, keep the object identity, method, environment, result, and source reference.
5. Keep `not run`, `blocked`, `failed`, and `passed` different. Do not replace unknown results with results that show success.
6. Make sure that shorter wording keeps authorization, ordering, conditions, and recovery guarantees.

For example, write:

> If the worktree has active writers, keep the worktree. Continue work independently in a different worktree.

Do not replace this with "Clean up when safe."
Before you use the document for acceptance, publication, a change of responsibility, or resource removal, complete its review.
